# session-crew v2: analysis

Asked by the maintainer on 2026-10-25, after the kcalloc ecosystem's git flow was installed in his
own hooks the same day: *"vorrei che anche il flusso di git farebbe parte della skill in futuro e
cio' riguarda solo l'ecosistema di kcalloc o dei progetti che collego ad esso"*, and on the
configuration: *"a me piacerebbe che lo user lo facesse direttamente in chat con le varie
opzioni"*. This file is the analysis to approve before any code; its decisions are V1 to V10 in
section 9. Nothing here is built.

## 1. What v2 adds

v1 ([design.md](design.md)) hands a session over and keeps a night going. v2 makes the plugin
carry the workflow a project is run with, configured by the user in chat:

1. **`/setup`**: the project's configuration made and changed in chat, with options to choose from
   (section 4).
2. **The git flow** of a project: one door through which its sessions push and tag the linked
   repositories, with the checks the table names; a public repository and a delete on a remote only
   on the user's yes (section 5).
3. **The unattended mode** that v1 only reads (`unattended.status_command`): turned on and off by
   the user's words, its limits written in the configuration (section 6).
4. Later, as decided on 2026-10-21 ("Due tempi"): the agents' model and the sessions' messages
   (section 7).

**A project's flow, never a global rule.** Everything v2 adds acts only for a folder that has a
`project.json`, and only on what that file names. In a folder with none, the plugin's guards say
nothing: what the user wants everywhere (his punctuation, his secrets) stays in his own hooks,
outside the plugin.

## 2. Where things are today

kcalloc's workflow lives in the maintainer's hooks, `~/.claude/hooks`, written for it:

| File | Does | v2 |

| `guard_bash.py` | the door's line and session, remote deletes, writes to the configuration; also his dashes, co-author trailers, secrets and real diary | splits: the door, the deletes and the configuration move; the rest stays his |

| `kc_mode.py` | the full mode: his words on and off, its state, `status` | moves in V2's second step (section 6) |

The table is already where v2 will read it: the field `repos` of the project's `project.json`,
written on 2026-10-25. kcalloc becomes the first configured project without moving its data.

## 3. Facts to rest on (Claude Code's documentation, read 2026-10-25)

1. **A plugin's PreToolUse hooks** answer `permissionDecision` (`allow`, `deny`, `ask`, `defer`)
   with the same effect as the user's, and run beside them: hooks from settings and plugins merge,
   none is deduplicated. When they disagree, **deny wins, then defer, then ask, then allow**
   (code.claude.com/docs/en/hooks.md, decision control). So a plugin can never loosen what the
   user's own hooks deny, and the user's deny of a command stays his.
2. **Permission rules come after the hooks**: a `deny` rule in settings blocks a call a hook asked
   for, and an `ask` rule prompts even when a hook allowed it (permissions.md). That is why
   kcalloc's `Bash(git push *)` moved from deny to ask on 2026-10-25: a remote delete could not be
   asked for otherwise.
3. **In auto mode a hook's "ask" still shows the prompt**; the classifier can deny, never approve
   silently (hooks.md). What happens under a mode that skips permissions is not documented.
4. **Plugins have a configuration of their own**, `userConfig` in `plugin.json`: typed values
   (string, number, boolean, directory, file, options, multiple, sensitive) asked when the plugin
   is enabled, kept in the user's `settings.json` under `pluginConfigs`, sensitive ones in the
   system's credential store, and passed to hooks as `CLAUDE_PLUGIN_OPTION_<KEY>`
   (plugins/manifest-reference.md). It is per user, not per folder, and holds flat values, not a
   table of repositories: it fits a default such as the language, not a project's flow (V10).
5. **A plugin's data folder**, `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`), survives
   updates and is **deleted on uninstall** unless `--keep-data`. The configuration stays in
   `~/.session-crew/<slug>/`, as in v1: an uninstall must not take a project's table with it.
6. **A plugin's `bin/`** is on the Bash tool's PATH while it is enabled, and
   `${CLAUDE_PLUGIN_ROOT}` is substituted in skill bodies but is not in the Bash tool's
   environment. **The door is not put on PATH**: a session could put a script of the same name
   earlier on it, and the guard would then let through a line that runs something else. The door
   runs by its absolute path, the one the guard computes from its own location, and the guard asks
   before any write into the plugin's folder.
7. **AskUserQuestion**: the documentation sets no limit, the tool itself takes 1 to 4 questions a
   call with 2 to 4 options each, plus the free answer. `askUserQuestionTimeout` may close an
   unanswered question: `/setup` then writes nothing and says where it stopped. A skill can forbid
   the tool (`disallowed-tools`); `allowed-tools` only pre-approves.
8. **A plugin disabled, updated or installed** reaches a running session only after
   `/reload-plugins` or a new session (plugins/loading.md). Each open tab keeps the guards it
   loaded; section 8 depends on it.

## 4. `/setup`: the configuration in chat

**What the user sees.** `/setup` (or `/session-crew:setup`) in a session of the folder:

1. **What is there.** The current configuration, if any, shown as a short table; then what the
   skill found by itself: the git repositories under the folder (and the ones the table already
   names elsewhere), each origin, whether GitHub holds it public or private (asked without
   credentials), and the sessions the user has named in this folder. What it found is offered for
   confirmation, never asked again.
2. **Questions in rounds**, each a question with its options and the free answer "Other":
   - general: the language, the two sizes (400 and 800 MB), whether nights are used and the phrase
     that starts one;
   - the sessions: for each, its role and the mains it owns;
   - the repositories, one question each: linked and pushed by which session, or not linked; then
     the checks before its push (none, the messages only, a preset such as Go's or Python's suite,
     or a command of its own); then its tags (the user's, or through the door, and where the
     version is written).
3. **The summary**: what changes against the current file, repository by repository.
4. **The write**, through the script alone (`crew.py config apply <draft>`), which validates the
   draft and writes it. The plugin's guard asks the user before that command runs; in the
   unattended mode it refuses.

**Why the write asks.** The file decides who may push what. A session that could write it alone
could give itself any right: the user's answers come in chat, the write still waits for his yes.
The same guard asks before any other write to `project.json` (an Edit, a Write, a shell redirect).

**Under Copilot** there are no option questions: the skill asks the same rounds as numbered lists
and the user answers with the number. Copilot has no PreToolUse guard in VS Code to ask before the
write (v1's design, section 9), so there the script asks for a typed confirmation itself (V8).

**Rounds of four.** AskUserQuestion takes up to four questions a call (section 3, 7), so a folder
with ten repositories takes three rounds for them. A repository the table already names is offered
as "unchanged" first. An answer that does not come (the tool's timeout) ends the setup with nothing
written.

## 5. The git flow

The same flow as kcalloc's (its `guidelines/git.md`, 2026-10-25), with the kcalloc names taken out:

- `python3 -I <plugin>/scripts/crew.py push <repo>` and `... tag <repo> vX.Y.Z`, by the plugin's
  absolute path (section 3, 6), alone on their line, from a session the table names among the
  repository's pushers, never from one of its agents (the guard reads the registry as v1's rename
  hook does). `/push` and `/release` are the skills that write that line.
- Before anything leaves: main checked out; origin, for fetch and push, the table's repository;
  fast-forward onto origin's main; a private repository still private; the commits' messages held
  to the project's rules; the table's checks in a clean worktree of HEAD; for a tag, the next patch
  or minor, written where the table says, never moved.
- **Public**: the guard asks the user each time; in the unattended mode it refuses.
- **Deletes on a remote** (`push --force`, `--delete`, a refspec with `+` or `:`, `--mirror`,
  `--prune`, a `gh` command that deletes, a DELETE to GitHub's API): the guard asks; at night it
  refuses. On the machine: nothing, as the maintainer decided.
- **Plain `git push`**: the plugin's guard denies it only in a repository the table names, and
  points at the door. Elsewhere it says nothing (the user's own rules decide).
- Every run in a log beside the configuration (`~/.session-crew/<slug>/releases.log`).

What was kcalloc's own becomes the table's: the checks (`go`, `frontend`, `unittest` today) become
argument lists with presets (V3); the message rules (no co-author trailer, no long or medium dash)
become a project's rules (V2); the version's place (CHANGELOG or VERSION) stays a field.

## 6. The unattended mode

v1 reads whether a night is on through a command of the project's (`kc_mode.py status` for
kcalloc). v2 can hold the mode itself: the start and stop phrases in the configuration (the start
phrase is already there), a state file only the user's words write, `crew.py mode status`, and the
limits a night allows written in the configuration and printed by `status`, for the project's
guidelines and the door to read (kcalloc's: `go test -p 8`, agents per session, simulators). Every
"ask" of the plugin's guards becomes a refusal while a night is on, as kcalloc's do since
2026-10-22.

## 7. Later: agents and messages

Decided on 2026-10-21 for after the first real night (done on 2026-10-22), and still to be
analysed on their own: the agents' model (implementer, reviewer, runner shipped by the plugin,
their briefs the project's) and the sessions' messages (SendMessage under Claude, a mailbox file
for Copilot, to be verified). V1 proposes to keep them out of v2.

## 8. Moving kcalloc

1. The plugin's door and guards built and tested on throwaway folders, with kcalloc's tests of
   2026-10-25 (`test_doors.py`, `test_release.py`) carried over.
2. kcalloc's `project.json` gains what the table does not hold yet (the message rules, the checks
   as lists); `/setup` shows it and the maintainer confirms.
3. `kc_release.py` and `kc_repos.py` are removed and `guard_bash.py`'s door goes, under his
   confirmation (they are his hooks); his own rules stay in them.
4. kcalloc's `guidelines/git.md` and `agents.md` §4 name the plugin's command.

A running tab sees the plugin's new guards only after `/reload-plugins` (section 3, 8). So the old
door stays until every open kcalloc tab has reloaded and found the new one; then 3 and 4 go in one
sitting, tests first, and the maintainer is told which tabs still hold the old guards.

## 9. Decisions

**Decided by the maintainer on 2026-10-25, all as recommended** (*"vado di consigliate Le decisioni
V1…V10 sulla v2 di session-crew"*): V1 (a), V2 (a), V3 (a), V4 (a), V5 (a), V6 (a), V7 (a), V8 (a),
V9 (a), V10 (a). Section 11 is the design of v2.0 that follows from them.

- **V1, what v2 holds.** (a) `/setup` and the git flow first (v2.0), the unattended mode next
  (v2.1), agents and messages after their own analysis (recommended: each step usable alone, and
  kcalloc moves in two small steps); (b) all four together.
- **V2, the commits' rules.** (a) A project's list in the configuration, offered by `/setup`, with
  kcalloc's two (no co-author trailer, no long or medium dash) (recommended: they are the
  maintainer's habits, not every user's); (b) kept fixed in the door.
- **V3, the checks.** (a) Argument lists per repository, with presets `/setup` offers (Go's vet,
  test and govulncheck; Python's unittest; a frontend's typecheck and tests when its folder
  changed) (recommended: a new project needs no code); (b) named kinds only, as today.
- **V4, hosts other than GitHub.** (a) GitHub only in v2: another host's repository is refused by
  the door, since its visibility cannot be checked the same way (recommended); (b) any host, the
  visibility taken from the table without a check.
- **V5, the configuration's write.** (a) Through `crew.py config apply` alone, which the guard asks
  the user before (recommended); (b) any write, asked.
- **V6, the names.** (a) `/setup`, `/push <repo>`, `/release <repo> vX.Y.Z`, each also as
  `/session-crew:<name>` (recommended); (b) all under one, `/crew setup`, `/crew push`.
- **V7, a folder with no configuration.** (a) The plugin's guards say nothing there (recommended:
  the flow is the project's, never global); (b) they deny `git push` everywhere.
- **V8, Copilot.** (a) `/setup` readable there, its write confirmed by a typed answer the script
  asks for, no door (no guard can hold it there) (recommended); (b) `/setup` for Claude Code only.
- **V9, the order of the move.** (a) kcalloc moves at v2.0's end, in one sitting with the
  maintainer there, his hooks keeping his own rules (recommended); (b) the plugin built and left
  beside his hooks until he decides.
- **V10, `userConfig`.** (a) Only for the plugin's defaults (the language), the project's flow in
  `project.json` through `/setup` (recommended: it is per user and flat, section 3, 4); (b) not used.

## 11. v2.0: the design

V1 (a): v2.0 is `/setup` and the git flow; the unattended mode's own state is v2.1. The v1 patch of
section 10 goes first, on its own.

### 11.1 Files

| File | Holds |
|---|---|
| `scripts/project.py` | the new fields of `project.json`, their validation, a draft's diff and its write |
| `scripts/repos.py` | the table: entries, presets of checks, GitHub's URL and visibility |
| `scripts/door.py` | push and tag, ported from kcalloc's `kc_release.py` |
| `scripts/guard.py` | the PreToolUse hooks for the Bash tool and the file tools |
| `skills/setup/SKILL.md`, `skills/push/SKILL.md`, `skills/release/SKILL.md` | the three commands |
| `hooks/hooks.json` | the two PreToolUse entries beside v1's hooks |

`crew.py` gains the subcommands `config` (`show`, `discover`, `apply`), `push` and `tag`. Every file
stays under about 300 lines; stdlib only, as v1.

### 11.2 The new fields of `project.json`

```json
{
  "commit_rules": {"no_coauthor": true, "forbid": ["\u2013", "\u2014"]},
  "repos": [
    {"name": "kcalloc-core", "path": "~/code/go/kcalloc-core", "github": "debug922/kcalloc-core",
     "visibility": "private", "pushers": ["kcalloc"], "checks": ["go"],
     "tags": {"version": "changelog", "annotated": false}}
  ]
}
```

- `commit_rules` (V2): what the door refuses in the messages of the commits it pushes; absent, none.
  `forbid` holds characters, written in the file as JSON escapes.
- `repos`, one entry a repository, as kcalloc's table of 2026-10-25, with `checks` (V3) a list
  whose items are a preset's name or an object `{"run": [argv], "in": "dir", "when_changed": "dir",
  "in_repo": false}`. The presets: `go` (with `GOWORK=off`: `go vet ./...`, `go test -count=1 -p N
  ./...`, `govulncheck ./...`, N 2 under `nice` by day and 8 while a night is on), `unittest`
  (`python3 -I -m unittest discover -s tests`), `frontend` (`npm run typecheck` and `npm test` in
  `frontend`, with `CI=true`, in the repository itself because of its `node_modules`, only when
  `frontend` changed since the last tag or origin, refused when it holds uncommitted changes).
  A check runs in a clean worktree of HEAD unless it says `in_repo`.
- `github` only (V4): a repository whose origin is not GitHub's cannot be in the table.
- A table that cannot be read, or an entry not of this shape, refuses every door command.

### 11.3 `crew.py config`

- `config show`: the project's configuration as it is read, and what it lacks.
- `config discover`: JSON for `/setup`: the git repositories under the folder (two levels) and those
  the table names elsewhere, each with its path, origin, GitHub name and visibility (`private`,
  `public`, or `unknown` when GitHub could not be asked), whether the table already names it; the
  sessions named in this folder (the registry, names given by the user only); the current file.
- `config apply <draft>` (V5): validates the draft, prints what changes field by field and
  repository by repository, keeps the previous file as `project.json.prev`, and writes the new one
  through a temporary file and a rename. A draft lives in `~/.session-crew/<slug>/drafts/`.
- The guard asks the user before `config apply` runs and before any other write to `project.json`
  (an Edit, a Write, a shell redirect or copy), and refuses both while a night is on.

### 11.4 `/setup`

Section 4, with the discover above as its first step and `config apply` as its last. Under Copilot
(V8) the same rounds as numbered lists, and the skill prints the `config apply` line for the user to
type in his own terminal: there no guard can stand between the session and the write.

### 11.5 The door

`python3 -I "<plugin>/scripts/crew.py" push <repo>` and `... tag <repo> vX.Y.Z`, with every check of
kcalloc's door (section 5), read from the project of the session's folder; the log in
`~/.session-crew/<slug>/releases.log`. `/push` and `/release` (V6) write that line, the plugin's
path filled in by the skill's `${CLAUDE_PLUGIN_ROOT}`.

### 11.6 The guard

For the project of the event's folder; with no `project.json` there it says nothing (V7):
- **the door's line**: exactly the plugin's own `crew.py` (the guard computes the path from its own
  location), alone on its line, from a session the table names among the repository's pushers,
  never from an agent; a repository outside the table, a tag where the table gives none, or a table
  that cannot be read: refused; a public repository: asked;
- **`git push`** in a configured project: refused and pointed at `/push`, unless the guard resolves
  the repository (`-C` or the folder) and the table does not name it; a push that deletes or rewrites
  on the remote (`--force`, `--force-with-lease`, `--delete`, a refspec starting with `+` or `:`,
  `--mirror`, `--prune`): asked;
- **`git tag`** creating or deleting a tag in a repository of the table: refused (the door makes
  tags);
- **GitHub**: a `gh` command that deletes, a DELETE to its API through `gh api` or `curl`: asked;
- **the configuration**: `config apply`, any write to `project.json` or into the plugin's folder:
  asked;
- **at night** (the project's `unattended.status_command` says so): every ask is a refusal, with the
  reason;
- a crash on a command naming the door refuses; any other crash lets the command through with a line
  on stderr, as v1's hooks.

The user's own hooks keep what is his (punctuation, secrets); deny wins over ask whichever hook says
it (section 3, 1).

### 11.7 Tests

kcalloc's `test_doors.py` and `test_release.py` of 2026-10-25 ported to the plugin's harness
(temporary `SESSION_CREW_HOME` and `CLAUDE_CONFIG_DIR`, bare repositories as origins, GitHub
stubbed), and for each part: the fields' validation, `config apply` (the diff, the previous file,
the atomic write), `config discover` (with a stubbed GitHub), every rule of the guard by day and at
night, a folder with no configuration left alone.

The unattended mode's own state and limits (v2.1), the agents and the sessions' messages (after
their analysis), and kcalloc's move onto the plugin (V9: at the end of v2.0, with the maintainer
there). The version is 0.2.0; its tag is the maintainer's.
